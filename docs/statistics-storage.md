# 统计存储

统计保存在运行目录下的 `data/stats.db`，使用无 CGO 的 `modernc.org/sqlite v1.61.1`。
启动自动创建目录、数据库和 Schema；未知 Schema、损坏文件、不可写目录或丢失去重密钥会明确报错，不清空重建旧库。

## 统计口径

- 用户和群：各 Bot 在当前保留期内独立去重，再按当前存在的 Bot 求和；同一用户出现在两个 Bot 中计两次
- 发送与接收：保留期内的实际计数；沙盒捕获回复不计为 QQ 发送
- 今日 DAU：统计时区当天的用户去重；没有新消息也会随日期切换
- 小时图：当天 00–23 点，共 24 个槽；缺失槽填 0，夏令时重复的钟表小时合并
- 历史图：按日聚合，日期递增，无记录日期填 0，最多查询 90 天且不超过保留期
- QPS：沿用接收加发送的每秒平均，窗口为最近 60 秒；读取时也推进过期桶，重启归零

默认保留 90 天。7/30/90/180/365 天均包含今天，例如 7 天为今天及前 6 个日历日；`0` 表示永久保留。
修改保留期后，查询立即采用新范围。已删除的数据不会因延长保留期恢复。
删除 Bot 不删除其保留期内历史，但会将其排除在总体统计之外；重建相同 Bot ID 视为恢复同一逻辑 Bot 的历史。更换 Bot 配置保留其统计归属。

## Schema v1

| 表 | 主键/索引 | 内容 |
| --- | --- | --- |
| `hourly` | PK `(bot, day, hour)`；索引 `day` | `sent`、`received` 计数，小时限制 0–23 |
| `identities` | PK `(bot, kind, day, digest)`；索引 `day` | 用户/群的 HMAC-SHA256 摘要 |
| `metadata` | PK `key` | 数据库时区、上次清理时间、上次计划清理日期 |

通过 `PRAGMA user_version=1` 管理版本；首次创建在事务中完成。升级必须显式迁移，较新版本不会被旧程序覆盖。
没有消息正文、原始 OpenID、AppSecret 或 Access Token 列。

`data/.stats-hmac-key` 是单独的 32 字节随机服务端密钥，文件权限 0600，不返回 API 或写入日志。
HMAC 输入包含 Bot、身份类别和原始 ID，使用 JSON 数组编码避免拼接歧义；日期作为去重主键的一部分。
摘要跨日期稳定，使同一用户在保留期内只计一次；每日记录又可支持 DAU 和过期删除。
原始身份在进入缓冲前已转换为摘要。

备份时同时保存数据库和密钥。推荐停止程序后复制；运行中应使用 SQLite 一致性备份，不能只复制可能尚有 WAL 数据的主文件。
已有数据库缺少密钥时拒绝启动，避免重新生成密钥后重复计数。

## 写入与关闭

一个工作协程负责 SQLite，连接数为 1；启用 WAL、5000ms Busy Timeout、`synchronous=NORMAL`。
消息处理不执行 SQL：记录进入最多 4096 项的缓冲，工作批次最多 256 项，每秒或满批提交一个事务。
统计查询先提交此前排队的记录，再读取数据库，不把前端刷新当作新计数。
BotManager 不在数据库操作期间持有全局 Bot 锁。

事务失败会回滚、保留失败批次并每秒重试；不继续扩展失败批次。
缓冲满时不阻塞 QQ 事件处理，拒绝新统计记录，并记录错误及 `dropped_events`。
`GET /api/stats/storage` 返回 ready/degraded、最近错误、待提交条数和运行期间丢弃条数，设置页显示异常。
丢弃计数在进程内持续可见；重启后重新计数，日志按现有日志策略保留。

正常关闭先停止 Bot、插件和 HTTP 请求，再排空统计缓冲、提交并关闭数据库。
失败会输出明确的关闭错误。正常负载下未提交窗口约为 1 秒或一个批次；繁忙、积压或数据库失败时不能承诺固定秒数。
异常退出会失去未提交的内存记录，最多为缓冲和失败批次共 4352 项；这不包括此前因满队列已明确丢弃的记录。
已提交 WAL 可跨进程重启恢复，突然断电的持久性仍受 NORMAL 同步和操作系统影响。
只支持一个 ShizukuBot 进程写同一数据目录。

本环境 `BenchmarkBatch`（GOMAXPROCS=4，Linux amd64）为 **30378 ns/op**，每次为一条接收和一条用户去重记录、每 128 次等待提交。
这约为 3.3 万次此测试操作/秒，不代表 QQ 接入吞吐或不同磁盘上的保证。

## 清理计划

默认 `Asia/Shanghai` 每天 `03:00`。配置使用 IANA 时区；Windows 构建内置 tzdata。
时区与数据库绑定，创建后不能通过在线设置修改；离线配置与数据库时区不符也拒绝启动，防止历史日期分桶混用。
清理时间可在线修改，格式严格为 `HH:mm`，不重启 Bot 或主程序。

启动时补查并清理过期行；计划任务由现有单个工作循环检查，不新增定时器或任务队列。
计划清理日期写入数据库，每个本地日期最多尝试一次；失败记录日志/状态，可手动重试或等待下一天。
春季跳过的时间在当天第一个已超过指定时刻的检查点执行；秋季重复小时不重复执行。
手动清理仅删除早于保留边界的 `hourly` 和 `identities` 行，永久保留时不删这些行。
删除和清理时间更新在同一个事务内完成；消息仍可进入有限缓冲。

每次清理不运行全库 VACUUM。SQLite 复用空闲页，删除后主文件大小不一定立刻下降；状态大小包含 DB/WAL/SHM。
沿用 SQLite 的 WAL 自动检查点和最后连接关闭处理，避免清理时强制截断 WAL 与写入争锁。

## 接口

均沿用现有管理员认证与响应包装 `{code,message,data}`：

| 接口 | 用途 |
| --- | --- |
| `GET /api/stats` | 总体保留期统计、当天小时槽、时区与保留天数 |
| `GET /api/bots/{id}/stats` | 单 Bot 统计 |
| `GET /api/stats/history?days=7\|30\|90` | 历史每日统计；可加 `bot_id`，其他范围拒绝 |
| `GET /api/stats/storage` | 状态、大小、错误、缓冲和清理信息 |
| `POST /api/stats/cleanup` | 使用已保存策略清理过期数据，无“清空全部”功能 |

原有汇总计数字段保持；小时结果保留 `Hour/Sent/Received`，同时提供前端使用的小写字段。
新历史记录为 `date/sent/received`。只有当前 Bot 的数据参与总体统计。
