# 规则与自动回复使用指南

规则是普通数据，适合无需编程的文本自动回复。Go 插件继续承担复杂逻辑；本功能不改变插件 SDK、Registry 或编译方式。

## 创建、测试与启用

1. 登录管理员账号，进入导航中的“规则”（`/#/rules`）。桌面 Rail 和手机 Drawer 都有入口。
2. 选择已经添加的真实 Bot，点击“新建规则”。新规则默认禁用，ID 自动生成且不可编辑。
3. 填写名称、触发方式和关键词，例如“包含 / 你好”；填写回复“你好！”。
4. 选择群聊、C2C 或两者。群 ID 列表为空表示不限群；填写列表时仅限制群聊，**不会限制 C2C**。如果只想在指定群生效，还须选择“仅群聊”。
5. 在“规则测试”填写模拟消息、来源及群 ID，点击“测试草稿（临时启用）”。当前草稿在本次测试中临时按启用评估，其他规则保持其保存状态；不会保存或开启生产规则。
6. 检查按顺序列出的命中事实、预期回复、停止及限制原因。测试仅捕获回复，不发送 QQ 消息，也不调用生产插件。
7. 保存规则，确认后用“立即启用”；也可勾选“启用”后保存。后续新事件立即读取新快照，无需重新编译、重连或重启。

编辑、切换 Bot/规则/页面、刷新和重置均处理未保存修改。保存失败保留草稿，不会显示成功；版本冲突意味着其他管理员已更新同一 Bot，请复制需要保留的内容，刷新后重新编辑，不能直接覆盖新版本。

列表支持搜索和启用状态筛选。立即启停、删除均保存当前 Bot 的整个规则集，不影响其他 Bot 或插件实例。删除前会确认。已经开始的事件允许按旧快照完成，启停和删除作用于后续读取新快照的事件。

## 匹配、顺序与回复

| 设置 | 实际语义 |
| --- | --- |
| exact | `events.Event.Message` 完全等于关键词 |
| contains | 消息包含关键词 |
| prefix | 消息以关键词开头，例如 `天气 ` 包含结尾空格 |
| 大小写、空白 | 区分大小写，不 trim 关键词或消息，不做 Unicode 归一化 |
| 条件 | 触发器 AND 来源 AND 群范围；群范围仅用于群消息 |
| 顺序 | priority 从高到低；相同优先级按 ID 的 ASCII 升序，与创建或页面顺序无关 |
| stop_on_match | **回复成功后**才停止后续规则，默认新建为 true；不阻止 Go 插件 |
| 发送失败 | 记录失败并继续后续规则；缺少 Reply、返回 error 和同步 panic 都有错误结果 |
| 单消息限制 | 最多 **3 次发送尝试**，包括失败；后续命中标为 limited |

仅处理现有 `group_message`、`group_at_message`、`c2c_message` 及对应来源。复用现有 Dispatcher 的消息身份去重：同一消息 ID 的群消息/群 @ 事件共享去重身份，不建立内容指纹；不同消息 ID 的相同内容仍可分别执行。没有可靠身份时保持原 Dispatcher 的保守策略。

现有顺序是 **核心内置指令 → 规则 → Go 插件**。`/help`、`/status`（或 Bot 配置的指令前缀）、`#shizuku` 由现有纯判断保留；规则和插件均跳过这些命令。普通事件仍会交给插件，规则的停止策略只结束本次规则链。`plugins/autoreply` 保留且不迁移、不自动禁用；与规则配置相同关键词时可能同时回复。

唯一动作是 `reply_text`。回复通过当前事件原有的 Reply 能力发送，不直接调用 QQ SDK、不生成新的入站事件。规则模板只做一次白名单字面替换：

| 占位符 | 值 |
| --- | --- |
| `{用户ID}` | 当前事件用户 ID |
| `{群ID}` | 当前群 ID，C2C 中为空 |
| `{BotID}` | 当前 Bot ID |
| `{消息内容}` | 当前消息原文 |

未知占位符原样保留；插入的用户文本不会再次展开。没有 Go/Shell/JS 表达式或动态函数。展开前检查大小，展开后为空白的回复会受限并继续后续规则。

## 限额

| 项目 | 上限 |
| --- | --- |
| 每 Bot 规则 | 100 条 |
| ID | 1–64 个 ASCII 字母/数字/下划线/连字符，首位为字母或数字 |
| 名称 | 非空白 UTF-8，128 字节 |
| 优先级 | -1000 至 1000 的整数 |
| 关键词 | 非空 UTF-8，1024 字节；纯空白可作为字面关键词 |
| 回复模板 / 展开回复 | 非空白，4096 / 8192 字节 |
| 消息输入 | 65536 字节 |
| 群 ID 列表 | 32 个，不重复；单 ID 128 字节，无空白或控制字符 |
| 管理请求 / 文件读取 | 1 MiB / 2 MiB |
| 发送 / 执行 | 3 次尝试 / 默认 5 秒合作取消 |

这些是字节限额，中文通常占多个字节。前端检查常见缺项，最终由 Go 校验完整规则集。正则、冷却、用户 ID 筛选、任意条件树和其他动作没有实现。

## 数据与 API

`data/rules/<sha256(BotID)>.json` 按 Bot 保存，不使用 Bot/规则 ID 拼接文件路径。格式包含 `schema_version: 1`、`bot_id`、`revision` 和 `rules`。每次完整验证后写同目录临时文件、Sync/Close，再 Rename，成功后才发布内存快照；保存失败保持旧快照。不可解析、未知版本或错误 Bot 范围的文件保留并报错，不自动清空覆盖。运行中只支持一个程序实例写同一目录；不要手工修改已缓存文件，离线备份/恢复应停止程序。

全部接口需要管理员登录，沿用现有同源/CSRF 检查和 API envelope `{code,message,data}`。业务错误仍使用项目现有 HTTP 200 + code 规范；认证、来源拒绝及请求过大使用对应 HTTP 状态。

| 方法及路径 | 用途 |
| --- | --- |
| `GET /api/bots/{id}/rules` | 读取真实 Bot 的版本化规则集，无数据时 revision 为 0 |
| `PUT /api/bots/{id}/rules` | 一次性替换，提交 `{revision,rules}`；创建/修改/启停/删除均使用此原子操作 |
| `POST /api/bots/{id}/rules/test` | 测试保存规则或显式草稿；只捕获回复 |

PUT 必须传入读取到的 revision 和完整 rules 数组，`[]` 删除全部。不能通过 body 指定另一个 Bot，未知字段被拒绝。修订冲突为 envelope `code:409`，附带当前 revision，不做自动合并。成功返回新 Set。示例：

```json
{
  "revision": 0,
  "rules": [{
    "id": "greeting", "name": "问候", "enabled": false, "priority": 100,
    "trigger": {"type": "contains", "value": "你好"},
    "conditions": {"sources": ["group", "c2c"], "group_ids": []},
    "action": {"type": "reply_text", "text": "你好！{用户ID}"},
    "stop_on_match": true
  }]
}
```

测试请求：

```json
{"message":"你好","source":"group","group_id":"example-group","user_id":"example-user"}
```

测试 `source` 只接受 group/c2c；群聊须有有效 group_id，C2C 的 group_id 须为空。可附带完整 `rules` 数组测试草稿；省略/null 使用保存版本，`[]` 测试空草稿。API 不会暗中启用禁用规则，只有页面“测试草稿”明确提交当前规则 `enabled:true` 的临时副本。结果包含 bot_id、revision、draft、eligible、skip_reason、attempts、replies、traces；traces 按实际顺序报告 enabled/evaluated、各条件事实、matched、status、reason 和预期 reply_text。测试中的 replied 表示成功捕获，不能据此推断真实 QQ 平台接受发送。

生产失败使用现有日志系统记录 Bot/规则 ID 和原因类别，不记录完整用户消息或 SDK 内部错误。规则页提供配置与测试结果，没有新增大型状态/日志平台。

## 部署边界

规则数据更新不涉及 Go 动态加载。部署仍只需 Go 工具链构建后端与插件，WebUI 是原有 MDUI 2 普通 JavaScript；浏览器资源沿用现有 CDN。可信 Go 插件的功能沙盒不等于 OS 隔离，规则预览也不承诺 QQ 的实际发送权限、限频或客户端渲染结果。

Windows amd64 已交叉构建，未做 Windows 实机运行或文件系统故障测试。原子替换验证在 Linux；Go Rename 在非 Unix 文件系统不提供同等通用原子性承诺，且当前未对目录做额外 fsync，不宣称断电级事务耐久。
